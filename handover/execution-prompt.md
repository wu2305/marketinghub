## 一、最终目标与范围

基于现有 `index.html`、`assets/pages/*.html`、相关 vanilla JS/CSS 和浏览器中的实际表现，全量重建 React 界面及原有前端交互。按奥卡姆剃刀原则，尽可能提取所有具有独立意义或复用价值的组件，形成基础、组合、区块、页面各层级的完整 Storybook 档案。

最终必须同时满足：
1. 全部现有页面及其页内视图、区块、覆盖层、表单、详情和可达交互状态，可以仅由本项目 React 组件组合重建。
2. 新页面可以从公共入口 import 组件，替换内容、状态与回调进行组合，无需复制原始 HTML、业务脚本或中间 DOM JSON。
3. Storybook 能独立展示组件变体、真实交互状态及页面组合，并提供可复现的验证证据。

“奥卡姆剃刀”减少不必要的实现复杂度，不缩减需求：同构的视觉结构与行为共享；真正不同的结构保留专用组合。不要把每个 div 拆成组件，不要追求组件数量；也不要为了少几个组件而写万能列表、类型分支巨组件、schema 驱动页面引擎或插件框架。视觉相似不等于行为相同，一次性但有独立意义的复杂区块也可以是专用组件。

完整覆盖既有前端行为；不建设真实后端、AI 服务、鉴权系统或生产持久化。原 Demo 用硬编码回答、localStorage、定时器演示的状态，用确定性的本地故事状态/轻量演示容器重建。组件不依赖真实服务，也不强制保留原存储机制。不要以“没有后端”为由删掉界面与动作。

这些是全量重建要吸收的问题，不是要求无限重复审核，也不是要求先重写整个业务数据层。

## 三、参照与覆盖台账

以原始页面在浏览器中实际生效的视觉/行为为参照。检查脚本加载顺序、CSS 覆盖、query/hash 和 storage 初态；不能找到同名变量就认定它是最终来源。v22 文档用于核对其明确覆盖的表单规则；与运行结果冲突时记录具体差异与取舍，不推定某一份旧脚本或文档覆盖全站。

知识类型计数遵守现有 typeMeta 约定；它不自动决定列表数据、字段或所有流程。原始静态数据可整理为有来源的故事 fixtures，但不得以占位记录凑数量、混合不同实体层级、发明业务说明或默认 Published/Enabled。计数、抽样和完整分页数据要明确区分；若分页等行为需要原始全量数据，不能用抽样掩盖缺失。测试边界用的合成数据必须明确标为测试夹具，不冒充原始展示内容。

在 handover 第 2 节展开 17 个入口的覆盖台账，至少包含：
- 稳定页面/状态 ID，源文件、URL/query/hash、生效脚本/CSS。
- 区块、触发动作、初始数据与预期可见结果。
- 适用的默认、非默认、选中、展开、空、错误、禁用、校验失败、长内容、覆盖层和窄屏状态。
- 使用的公共组件/专用组合、层级、变体及复用位置。
- 对应 story ID、参数/交互步骤、行为和视觉验证证据、未完成原因。

列出原有可达状态及关键边界，不枚举无意义的笛卡尔积，也不要制造原 Demo 不存在的新产品功能。未知项标为待核实，不用“无”或“不适用”逃避盘点。首轮全量清单完成后立即进入实现，随发现继续补台账。

## 四、组件设计与故事原则

每处理一个页面/完整区块，执行：读参照 → 识别已有复用 → 确定最小必要边界 → 实现组件与局部行为 → 独立故事 → 页面组合 → 对照与行为验证 → 更新台账 → 下一条。

- 公共基础：tokens、图标、按钮、输入、标签、选择等，按实际需求提取。
- 组合控件：字段组、搜索/多选筛选、分页、菜单、提示等。
- 区块：导航、侧栏、Hero、卡片/表格、表单、图表、详情、弹窗/抽屉等。
- 页面：只负责使用这些组件组合原始布局；不复制大段已可提取结构。

层级帮助理解，不是强制多套 wrapper 的理由。优先 props/children/组合，只有同一概念的形态差异才用 variant；不同结构不要堆 mutually exclusive flags。共享标准样式也不意味着统一所有业务字段。状态与轻量规则只做到支撑已存在的界面/交互，不先建全站领域引擎。

遵守 AGENTS 的语义接口、具名回调、导航、useId、token、CSS 隔离、响应式、focus-visible、类型声明、枚举常量与公共导出约定。可以按真实组件边界拆分目前庞大的文件，但不作与交付无关的目录重组。默认沿用现有技术栈，类型可用 JSDoc/PropTypes，不为“现代化”额外进行全栈迁移。

对公开组件建立独立故事：必要变体、受控状态回写、Controls 和 Actions、可理解文档。展示性组件不虚构事件。页面故事也必须能操作，不能只打印日志；导航/保存等跨区块行为由轻量演示状态容器承接。使用 Storybook 提供的 args 同步能力或清晰的 React 状态接线，避免界面与 Controls 长期脱节。

每批只处理一个可独立验收的条目，形成可审查 diff/提交和证据。正常通过后直接推进下一条，不反复询问“是否继续”。遵守平台权限；未授权的发布/合并/部署不执行，远端权限不足不阻止本地实现。不要绕过权限，也不要为了等待某个外部动作停止其他可独立进行的工作。

## 六、验证必须证明什么

1. 构建：Storybook 和相关测试通过；故事基线不减少。确需合并冗余故事时先证明覆盖保留并按仓库约定处理，不能静默删除。
2. 实际故事：从真实故事渲染/接线验证输入、选择、筛选、分页、打开/关闭、校验、保存等相关动作。独立 Harness 可辅助，但不能代替实际故事验证。
3. 视觉：自动脚本在隔离浏览器上下文中加载原始页和 React 故事，固定视口/初态，验证预期页面及状态已加载，再串行截图，输出可读并排对照。1440px 基线必做，相关窄屏布局也要检查；长页下部与覆盖层不能漏掉。若 Chrome 不可用，可用 Playwright Chromium，记录环境差异。
4. 失败可见：导航失败、页面错误、必要资源 404、错误 story ID 或预期控件未出现，必须判失败，不能 catch 后继续报“通过”。确定性参照已有错误可登记为参照限制，不自动给 React 实现豁免。
5. 测试断言：验证用户可见行为和数据不丢失，而不是只检查实现函数、class 或与自身 fixture 相等。共用组件变更检查受影响使用场景。
6. 复用：公共入口组件在不依赖 .storybook 配置的 React 宿主正常显示/交互、资源可加载、样式不污染其他 UI。至少提供一个使用不同示例内容与布局的新组合，证明组件可组合而非原页换皮。

截图/临时产物存 /tmp，不提交二进制对照图。可重复脚本与场景配置应入库；后者只描述 URL/动作/期望，不存中间 DOM。记录命令、结论、路径和未通过项。人眼对照关注布局、排版、间距、密度、数据与状态，不能仅依靠像素阈值。不要编造“已肉眼检查”。

有意差异用于稳定接口、无障碍等有理由的调整，不能把未实现功能、占位列表、漏字段、错误布局永久包装成差异。未通过就是未完成；截图存在不等于已比较，构建通过不等于交互完整，故事数量不等于覆盖完整。
