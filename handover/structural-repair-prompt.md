你负责修复 Marketing Hub React / Storybook 重建中的结构性问题，并继续原有全量目标。请实施、验证、交付，不要仅重复审核或提交计划。保留现有有效组件和实现，不重启 DOM 复刻路线，不另建业务产品。

## 1. 目标与不可突破的边界

原始 Demo 的浏览器可达行为决定覆盖范围；React 组件的语义接口决定组合方式。两者必须同时成立。17 个页面及台账中的子视图、交互、表单、覆盖层仍在最终范围内。

当前纠偏批次的目标是：先使已实现部分能够被可信地验收、替换数据、组合复用，再继续 M4–M7。不得把完成纠偏批次说成全站完成，也不得先进行无边界的全库重构。

禁止：原始 HTML/iframe/DOM JSON 作为组件运行时、挂载 assets/js、万能页面 schema、全局业务状态平台、为了层级命名逐标签拆分、另建后端/真实 AI/持久化系统、以代码行数或组件数作为成功指标。允许保留复杂但有独立意义的专用区块。

## 2. 先确认基线，保护现有成果

读取 AGENTS.md、handover/README.md、CONTEXT.md 和当前 diff；核实分支、HEAD、origin/main 的真实祖先关系。不要 reset/stash/覆盖他人改动，不纳入 `.commandcode/`，不盲目切回 main 丢失未合并成果。必要时建立明确记录依赖关系的隔离工作区；遵守权限流程。

上次审核基线仅供定位，不可当作当前事实：02918b5 + 当时已有 8 个 tracked 修改，63 stories + 5 docs，10 条单测；P07 10 个场景断言通过，但 Principles 默认态人工视觉未通过。当前可能已变化，先确认，已修复项不返工。

已确认的根因线索：
- CityInvestDashboard 没有数据输入接口；报表搜索辅助函数固定读取 KNOWLEDGE_ASSETS；Copilot 部分答案正文直接读取演示常量。
- CockpitStory 的部分逻辑读取 COCKPIT.projects 而非传入的 args.projects，界面数据与交互数据可能分离。
- 状态分布于 story、page、organism 与模块全局，缺少明确归属；activeCopilotStream 为模块全局，取消范围超过单一会话。
- Campaign 任务 Object 编辑→Cancel→重开，原始保留输入而 React 丢失；不能归入永久有意差异。
- Interpreter 使用不符合参照的外壳；配对脚本 PASS 没有证明视觉一致。
- tokens 全局 reset、根路径资源、原始 HTML 导航地址与 Storybook staticDirs 可能掩盖独立宿主问题。

区分已运行复现与静态推断。Accounts 错参数漏洞上次复核已修复，Principles 数据来源也已修复；不要继续把旧结论写为现存问题。

## 3. 批次 A：修复验收机制，先让错误不能冒充完成

修改现有 scripts/visual-check.mjs 与配置，保持脚本规模适中，不新建测试平台。

1. 每次产物记录：HEAD、工作区差异指纹（覆盖 src/design/.storybook/验证配置及相关未跟踪源文件）、构建时间/构建指纹、运行命令、视口、URL、storage 种子、story ID 与参数。明确将新构建和本次运行绑定；发现源码变更后仍使用旧构建时失败或要求重建。仅记录当前 git HEAD 不足以证明产物归属。
2. 每场景分别输出加载结果、行为断言结果、人工视觉状态（pending/pass/fail）。机器不得默认填写人工 pass；缺审核就是 pending。自动退出码表达机器检查结果，输出明确说明不等于人工视觉通过。
3. 场景断言验证特有标题、选中状态、关键内容/数量及必要的错误区块排除。避免只断言外壳存在，也不要用 React 自己的 fixture 作为全部正确性依据。
4. 维护可重复负向检查：错 story/错 section 必须失败；另加布局回归检测，例如 Interpreter Hero 必须位于侧栏右侧，侧栏起点符合原始参照。负向检查在临时副本或测试注入中运行，不污染正式配置。几何断言使用合理容差，不能替代截图人工审核。
5. pageerror、关键资源失败、框架错误页不可忽略。console error 须失败或有精确且有依据的例外；禁止宽泛吞错。
6. 分别统计 stories/docs 和场景覆盖；台账保留稳定状态 ID 与场景映射，不以截图总数作为进度分母。

验收：正确场景机器通过；故意错误场景失败；未审图显示 pending；旧构建不能被当成本次代码的证据。

## 4. 批次 B：让数据、状态与展示各有明确责任

只按已暴露的依赖拆边界，不要求立即重排整个目录。先沿 Cockpit / CityInvest / ReportCopilot 这条纵向路径落实，再将同样原则用于后续页面。

合理依赖方向：
- 原始来源整理出的 fixtures、确定性模拟回答/数据生成属于演示侧。
- 展示组件和页面组合接受语义数据、状态、children 与具名回调；不隐式查演示数据，不读取来源 URL/storage 来决定内容。
- 演示状态容器连接组件与确定性数据；不依赖 Storybook API，可被故事和独立宿主共同使用。
- Story 文件主要声明 args/Controls/Actions 和状态场景。并非所有 useState 都必须抽走，只提取实际需要跨宿主共用的流程，避免复制同一业务接线。

具体要求：
1. 将混在 report-data.js 中的 fixture、纯运算和路由约定按职责最小拆开；纯计算函数显式接收所需数据，不能经另一个工具模块偷偷读取固定 fixture。
2. CityInvestDashboard 接受数据、文案、选项及必要筛选状态/事件；种子数据生成放演示侧，保留原参照数值和筛选结果。不要把每个 HTML 属性变成 prop，也不要为了“通用”发明新图表引擎。
3. 报表知识关联和搜索从宿主传入的数据得到；新 knowledgeIds 可以解析，新知识标题可以被搜索，不能与旧 KNOWLEDGE_ASSETS 暗中联结。
4. ReportCopilot 接受实际显示所需的答案与关联内容；rich/holistic 的专用呈现可保留，固定业务正文不能隐藏在展示组件里。
5. 页面需要的业务数据与文案有可替换入口。修复 CockpitStory 用 COCKPIT.projects 旁路 args 的问题；Controls 改数据后，展示和动作必须使用同一份数据。
6. 保持唯一公共入口、JSDoc、枚举常量和故事。目录拆分本身不算该批完成。

验收：通过公共入口注入明确标为测试夹具的另一组项目/城市/指标/知识关联/答案；不用改组件源码，显示、搜索、筛选和动作正确，且不泄漏旧 Demo 数据。随后回跑原始数据的行为与配对视觉，确保重构没有改写原产品。

## 5. 批次 C：统一状态归属与生命周期

为此次涉及的状态建立简短责任表，写入 handover 对应条目：谁持有、什么动作改变、关闭保留还是重置、New Session 如何处理、Controlled/Uncontrolled 约定。

- 会话答案、草稿、跨区块选择等由合适的流程宿主持有；hover、测量等局部呈现状态留在组件。不要机械地把所有局部状态提升到全局。
- Campaign 任务草稿关闭重开应保留，与原页一致；只有参照明确重置的动作才重置。同步检查 ModelFlow 的返回/关闭/重开路径，先查参照再定义预期。
- activeCopilotStream 改为会话/实例范围。一个会话里新回答取消旧流的原行为保留，但另一个实例不受影响。不能删除取消功能来躲避多实例问题。
- 处理受影响的滚动锁、Escape、焦点恢复与叠层。多个打开层不能因一个卸载就解除另一个的锁或错误恢复焦点。原有关闭语义和必要无障碍调整分别记录，不能臆造所有页统一的交互规则。
- 回调遵守具名对象约定，不把 DOM event 漏成公共业务接口。改动接口时同步所有调用方与 Actions。

验收包含：编辑→关闭→重开；返回→再进入；新会话；双实例同时流式显示；卸载其中一个；嵌套覆盖层的焦点/滚动恢复。断言最终用户可见状态，不只断言内部 setState 调用。

- 配对验证 overview、Principles 默认、分类筛选、搜索空态、展开、长页下部及至少一档窄屏。
- 核验共享外壳对 Business Term/Scenario 等已存在类型的影响；它们仍是过渡列表，不得借本次外壳修复标为专用视图完成。
- 撤销错误的“像素一致”历史结论并给出新证据；不要修改原始 Demo 或调整截图参数隐藏差异。

验收：参考状态与 React 状态相同，整体布局、排版、密度、遮挡和主要数据经实际查看通过；所有剩余差异具体登记。

## 7. 批次 E：提前建立最小独立宿主和导航闭环

建立可本地构建的最小 React 宿主，使用公共入口。它是复用验收夹具，不是新产品，不要求部署。

1. 不读取 .storybook 配置、不 import stories、不加载原始 HTML/原业务脚本；允许共享上述演示容器、fixture 和静态媒体，但不同内容用例必须独立注入。
2. scoped reset 不改变宿主已有按钮/链接/表单；导入组件前后检查宿主哨兵元素的计算样式。token 变量、字体注册与元素 reset 分开处理，不必为了隔离新增大型 Provider。
3. 字体/图片在宿主约定和非根 base path 下可用；明确安装/资源约定，不依赖 `/assets` 恰好由 Storybook 提供的巧合。
4. 至少实际跑通一个现有 React 导航闭环，例如 Cockpit 目录→项目→Dashboard→返回目录。确认点击之后仍在 React 宿主中，不能悄悄导航到原始 HTML 然后算 React 交互通过。
5. 保留 `<a href>`、正常浏览器导航/新标签语义。宿主可映射 href 并对其负责的内部导航使用明确路由适配；不要把导航改按钮，也不要无条件拦截所有链接。不强制引入路由库。
6. 对尚未实现的目标页如实标记覆盖缺口，不制造占位页声称完成，不要求本批为验证导航而先建完 M5/M6。
7. 同页两个实例、不同内容与不同布局组合的验证使用真正组件，不复制原页、不复制故事接线。

验收：独立构建通过，资源正常，内部导航闭环通过，宿主样式不受污染，双实例互不干扰。

## 8. 实施顺序、规模与交付

默认 A→B→C→D→E，依赖需要可局部调整并记录；每批只提交一个可独立验收条目，必要时继续细分。不把所有结构改动打成一个大 PR，不等待一个想象中的完美框架。

每批均需：相关测试、build-storybook、stories/docs 实数、真实故事交互、受影响页面配对截图和人工结论、修改组件的枚举 Controls、必要回归。共享组件影响多个页面时验证真实使用位置；不要无理由重复全套昂贵测试。

先保留原行为回归，再加能暴露根因的少量测试：不同数据、生命周期、两实例、错场景、导航留在 React、宿主样式。不能只把当前 fixture 和当前输出互相比较。

按 AGENTS.md 的顺序更新规则审核条目与 handover，唯一状态台账仍为 handover/README.md。不同结论明确分开：实现完成、机器检查通过、视觉人工通过、未验证。记录提交/dirty 指纹、截图路径、实际差异、最小下一步。

有意差异必须有来源与理由；漏行为、数据丢失、错误布局不能永久豁免。发现参照缺陷时记录证据和最小处理，不按“明显意图”自行扩展死代码功能。

纠偏完成后恢复 handover/execution-prompt.md 的全量推进：剩余七类知识视图、M5/M6、全站收敛。不允许把独立宿主演示或 Principles 单页当成最终交付。缺外部发布权限不妨碍本地实施；若被工具/时间限制迫使停下，准确列出剩余项，不报告完成。

最终回复用证据回答三件事：原页是否忠实、不同数据能否组合、脱离 Storybook 能否运行。列出已修根因、验证命令与结果、未完成范围，不仅罗列新增组件。
